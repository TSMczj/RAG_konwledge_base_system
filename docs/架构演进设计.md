## 一、背景

当前系统已经完成 M1：

- 10 份文档 / 4021 个 chunk；
- PDF / DOCX / TXT 解析、分块、Qwen 1024 维嵌入、Chroma 入库；
- `build_index.py` / `manage_index.py` 两个 CLI；
- 索引管理、软删除需求已经在 UI 原型中出现；
- Web API 已完成到 T-5.4：FastAPI 骨架、health、文档管理（含软删除/恢复/彻底删除）、聊天 SSE；
- Web 页面（聊天页/文档页）尚未接入，当前首页仍是占位页。

短期内系统只在本地单用户使用，没有上线计划。但未来可能：

1. 发给别人，每个人在自己电脑上运行一份；
2. 放到服务器上，让多个用户通过浏览器访问；
3. 每个用户使用自己的 DeepSeek / 百炼 API Key；
4. 用户之间知识库、文档、对话、配额互相隔离。

这三件事不应该等到上线前才改。当前 Web API 已把 `RequestContext` / `SecretProvider` / `tenant_id` 边界落下；剩余边界（SQLite 元数据、服务器适配）仍应在 M3 完成前保持最小改动。

## 二、结论摘要

### 2.1 总体决策

采用：

> **本地优先的模块化单体（Modular Monolith）+ 端口/适配器（Ports & Adapters）+ 从第一天预留租户维度。**

不采用：

- 现在就做微服务/Kubernetes；
- 现在就写完整多用户权限系统；
- 把 Chroma 当业务数据库；
- 把 API Key 存进浏览器或明文文件；
- 为了“未来可能”过度抽象每个类。

### 2.2 五条核心决策

| # | 决策 | 原因 |
|---|---|---|
| D1 | 所有业务数据带 `tenant_id`，本地默认 `"local"` | 未来多用户隔离的最小数据边界 |
| D2 | 引入 `RequestContext`，不再让核心逻辑依赖全局 `get_settings()` | 每个请求可能对应不同用户/Key/配置 |
| D3 | `SecretProvider` 抽象密钥来源：环境变量 / 本地加密 / 服务器密钥库 | 同一套业务代码支持单机与多用户 |
| D4 | 文档元数据放 SQLite（未来 Postgres），Chroma 只做向量索引 | Chroma 不适合承担用户、软删除、任务状态等事实数据 |
| D5 | 本地模式无认证、只绑 `127.0.0.1`；服务器模式必须认证后再取 tenant | 不把“本地便利”变成“公网裸奔” |

## 三、现状评估

### 3.1 已经做得好的部分

- `app/core/loader.py`、`splitter.py`、`embedder.py`、`vectorstore.py` 职责相对清晰；
- 文档解析、分块、嵌入、索引可以脱离 Web 独立测试；
- `build_index.py` / `manage_index.py` 已经把批处理逻辑从 UI 中分离；
- 文档哈希、chunk metadata、失败清单、扫描件告警等基础能力已具备；
- 有 121 项测试和真实文档验收数据，后续重构有回归基线。

这些意味着：**不需要重写核心，只需要把边界收口。**

### 3.2 未来会疼的耦合点

#### ① 全局配置 + 启动时强制 Key

[`app/config.py`](../app/config.py)：

- `get_settings()` 使用 `lru_cache`；
- `DEEPSEEK_API_KEY` / `DASHSCOPE_API_KEY` 是必填 `SecretStr`；
- 配置在启动时校验，缺失直接 `ConfigError`。

单用户 CLI 没问题，但服务器多用户场景下：

- 不能用一个全局 Key 服务所有用户；
- 不能在启动时要求所有用户先配置 Key；
- 不能把“请求 A 的 Key”串到“请求 B”。

需要把配置/密钥从“进程全局”改为“请求上下文”。

#### ② chunk_id / 查询 / 删除没有租户维度

[`app/core/vectorstore.py`](../app/core/vectorstore.py) 当前：

```text
chunk_id = {file_hash}-{chunk_index}
```

查询和删除按 `file_hash` / `source_file`：

```text
_ids_where({"file_hash": file_hash})
_delete_where({"source_file": source_file})
```

多用户共用一个 collection 时：

- 相同文件在不同租户下 chunk_id 冲突；
- 删除 A 的文件可能误删 B 的同名/同内容文件；
- 少写一个 `tenant_id` 过滤条件就串数据。

这是最高风险项，必须在服务器化之前解决。

#### ③ Chroma 被当成文档数据库

当前 `list_files()` 从 Chroma metadata 反推文档列表；软删除、导入状态也挂在向量记录上。

这会导致：

- 文档列表、状态、任务进度与向量库强耦合；
- 未来要分页、搜索、审计、配额时，Chroma 不适合；
- 软删除需要更新所有 chunk metadata，成本高且容易漏。

目标应是：

```text
业务数据库（SQLite → Postgres）：文档、用户、任务、软删除状态、密钥元数据
向量库（Chroma → 托管向量库）：chunk 向量 + 检索所需 metadata
```

#### ④ 本地路径 / 单 collection 直接写死

当前 `CHROMA_DIR`、`UPLOAD_DIR`、`COLLECTION_NAME` 来自配置，`VectorStore` 直接打开本地 Chroma。

未来服务器需要：

- 对象存储而不是本地 `data/uploads`；
- Chroma Server / 托管向量库，而不是本地路径；
- 每个租户独立 collection 或强制 tenant 过滤。

需要 `VectorRepository` / `FileStorage` 适配器，而不是在业务层直接 `Path` / `Chroma`。

#### ⑤ 还没有 API 与认证层

`app/api/` 目前只有 `__init__.py`。这是好事：现在设计 API 契约，比写完再改便宜。

但必须从第一天就留出：

- `get_current_context()` 依赖；
- 本地模式默认 tenant；
- 服务器模式 session/token → tenant/user；
- 不信任客户端传入的 `tenant_id`。

## 四、设计原则

1. **本地优先**：本地单用户是主场景，不为假想规模牺牲体验。
2. **模块化单体**：一个部署单元、清晰模块边界；需要时再把 worker 拆出去。
3. **端口/适配器**：业务服务依赖 Protocol，不直接依赖 Chroma、SQLite、环境变量。
4. **租户从上下文来**：tenant 只能由认证/本地模式推导，不能由请求体指定。
5. **失败关闭**：没有 tenant 上下文、没有 Key、没有权限时拒绝，而不是退回全局默认。
6. **秘密最小化**：Key 只在需要时解密，不落日志、不进浏览器存储、不回传明文。
7. **渐进演进**：每个阶段都能独立运行，不搞“大爆炸重构”。

### 5.2 关键边界

| 边界 | 本地实现（现在/近期） | 服务器实现（以后） |
|---|---|---|
| 身份 | 固定 `tenant_id="local"`，无登录 | 登录 session/OIDC → tenant/user |
| 密钥 | 环境变量 → 本地 DPAPI/keyring | 每用户加密密钥库 + 主密钥/KMS |
| 文档元数据 | SQLite | Postgres |
| 向量 | 本地 Chroma，单 collection | Chroma Server / 托管向量库，按租户隔离 |
| 文件 | `data/uploads/` | S3/MinIO/对象存储 |
| 任务 | 进程内后台任务 | Redis + worker |
| 部署 | 单进程，127.0.0.1 | 容器/反向代理/TLS |

## 六、核心模型

### 6.1 Tenant

- 本地模式：一个固定 tenant，建议 `tenant_id = "local"`。
- 服务器模式：一个用户默认一个个人 tenant；未来可扩展“工作区/团队”。
- 所有业务表、向量 metadata、文件路径、任务、密钥记录都必须带 `tenant_id`。
- **tenant 不能由客户端请求体或 header 直接指定**，只能从认证上下文推导。

### 6.2 RequestContext

建议新增 `app/context.py`（名称可调整）：

```python
@dataclass(frozen=True)
class RequestContext:
    tenant_id: str
    user_id: str | None
    settings: Settings
    secrets: SecretProvider
```

应用服务只接收 `RequestContext`，不再直接调用全局 `get_settings()`。

本地入口：

```text
build_index.py / manage_index.py → LocalContext(tenant_id="local")
```

服务器入口：

```text
FastAPI dependency → get_current_context(request) → RequestContext
```

### 6.3 SecretProvider

```python
class SecretProvider(Protocol):
    async def get(self, tenant_id: str, provider: str) -> SecretStr: ...
    async def set(self, tenant_id: str, provider: str, value: SecretStr) -> None: ...
    async def delete(self, tenant_id: str, provider: str) -> None: ...
    async def status(self, tenant_id: str, provider: str) -> SecretStatus: ...
```

适配器：

| 适配器 | 场景 | 存储 |
|---|---|---|
| `EnvSecretProvider` | 本地/CI | 系统环境变量 |
| `LocalVaultSecretProvider` | 分发给别人、本机运行 | Windows DPAPI / keyring |
| `ServerVaultSecretProvider` | 服务器多用户 | AES-GCM 密文 + 主密钥/KMS |

要求：

- 只返回掩码状态，不返回完整 Key；
- 解密只发生在调用模型前，尽量缩短生命周期；
- 不写日志、不进 `.env`、不进 `localStorage`；
- 服务器不允许 A 用户读取/覆盖 B 用户的 Key；
- “管理员替别人配置 Key”只在“组织共享 Key”这种明确模型下允许，且要单独审计。

### 6.4 DocumentRepository

```python
class DocumentRepository(Protocol):
    def create(self, ctx, document: DocumentRecord) -> DocumentRecord: ...
    def get(self, ctx, document_id: str) -> DocumentRecord | None: ...
    def list(self, ctx, status: str | None = None) -> list[DocumentRecord]: ...
    def update_status(self, ctx, document_id: str, status: str) -> None: ...
    def soft_delete(self, ctx, document_id: str) -> None: ...
    def restore(self, ctx, document_id: str) -> None: ...
    def permanent_delete(self, ctx, document_id: str) -> None: ...
```

建议字段：

```text
id, tenant_id, file_hash, source_name, storage_key,
status(active/removed/deleting/failed),
pages, chunks, created_at, removed_at
```

`status` 是业务事实来源；Chroma 只保存向量和检索 metadata。

### 6.5 VectorRepository

```python
class VectorRepository(Protocol):
    def upsert(self, ctx, document_id: str, chunks: list[Chunk]) -> None: ...
    def query(self, ctx, embedding: list[float], k: int) -> list[RetrievedChunk]: ...
    def delete_document(self, ctx, document_id: str) -> int: ...
    def count(self, ctx) -> int: ...
```

实现策略：

- 本地：单个 Chroma collection，metadata 带 `tenant_id="local"`；
- 服务器：**优先每租户独立 collection**；如果共用 collection，repository 必须强制注入 tenant 过滤，并用跨租户测试兜底；
- 未来换 Qdrant/pgvector 时，只替换 adapter。

### 6.6 FileStorage

```python
class FileStorage(Protocol):
    def save(self, ctx, document_id: str, filename: str, data: bytes) -> str: ...
    def open(self, ctx, storage_key: str) -> BinaryIO: ...
    def delete(self, ctx, storage_key: str) -> None: ...
```

- 本地：`data/uploads/<tenant_id>/<document_id>/<filename>`；
- 服务器：S3/MinIO，key 前缀带 tenant；
- 不使用原始文件名做唯一标识，`document_id` 才是身份；
- 路径校验必须在存储层完成，防路径穿越。

### 6.7 JobService

```python
class JobService(Protocol):
    def enqueue(self, ctx, kind: str, payload: dict) -> str: ...
    def status(self, ctx, job_id: str) -> JobStatus: ...
    def cancel(self, ctx, job_id: str) -> None: ...
```

- 本地：`asyncio` / 线程池；
- 服务器：Redis + worker；
- 上传/重建都走 JobService，前端轮询接口不变；
- 同一 tenant 同一时间限制一个索引任务，避免并发写向量库。

### 6.8 AuthContext

```python
class AuthProvider(Protocol):
    async def resolve(self, request) -> AuthContext: ...
```

- 本地模式：直接返回 `tenant_id="local"`，无登录；
- 服务器模式：session/OIDC → user/tenant；未认证直接 401；
- 不自研密码学/登录协议；优先 OIDC、Passkey 或成熟库；
- 所有 `/api`（除健康检查）都依赖 `get_current_context()`。

## 七、数据模型与隔离

### 7.1 建议的业务表

```text
tenants(id, slug, name, created_at)
users(id, tenant_id, email, display_name, created_at)
documents(id, tenant_id, file_hash, source_name, storage_key,
          status, pages, chunks, created_at, removed_at)
document_versions(id, document_id, file_hash, version, created_at)
jobs(id, tenant_id, kind, state, progress, current, total,
     message, error, created_at, updated_at)
user_secrets(id, tenant_id, user_id, provider,
             ciphertext, key_version, updated_at)
chat_sessions(id, tenant_id, user_id, created_at)
chat_messages(id, session_id, role, content, created_at)
audit_events(id, tenant_id, user_id, action, target, created_at)
```

本地可以只实现 `documents` / `jobs` / `user_secrets` 的最小表；其他表后续补。

### 7.2 租户隔离规则

- 所有查询必须带 `tenant_id`；
- 所有删除必须同时带 `tenant_id + document_id`；
- 文件名不是身份，`document_id` 才是；
- 向量 metadata 必须包含 `tenant_id` / `document_id`；
- 跨租户测试必须存在：
  - A 的查询看不到 B 的 chunk；
  - A 删除不影响 B；
  - A 的 Key 不能用于 B 的请求；
  - A 不能通过 job_id 查询 B 的任务。

### 7.3 ID 方案

当前：

```text
chunk_id = {file_hash}-{chunk_index}
```

目标（服务器 Beta 重建时切换）：

```text
chunk_id = {tenant_id}:{document_id}:{chunk_index}
```

`file_hash` 继续作为内容去重/版本字段，但不再是全局唯一身份。

本地现阶段不必为了这个立刻重建 4021 个 chunk；在服务器 Beta 的一次全量重建中切换即可。**不要为了改 ID 反复消耗嵌入额度。**

## 八、API 契约边界

### 8.1 版本化

从第一天使用 `/api/v1/...`，避免未来破坏性变更。

### 8.2 唯一接口来源

具体路由、请求/响应字段、SSE 事件顺序、错误码、job 状态机，统一以 [API 契约](API契约-v1.0.md) 为准。本文只保留架构约束：

- 所有业务接口（健康检查除外）必须从 `RequestContext` 取 tenant/user；
- 本地模式固定 `tenant_id="local"`，不要求登录；
- 服务器模式必须先认证再解析 tenant，未认证 401、越权 403；
- 接口实现不得把 Key、完整文档内容写入日志。

### 8.3 软删除与 Key 的架构约束

具体语义见 [API 契约](API契约-v1.0.md)，本文只约束边界：

- 软删除：业务状态为 removed，向量与文件保留，检索默认排除；
- 恢复：只改状态，不重新嵌入；
- 彻底删除：业务记录 + 向量 + 原文件三处一致；
- Key：系统环境变量优先；缺失时读取 Windows DPAPI 本机加密存储（设置页写入）；服务器模式每用户加密密钥库。任何模式都不得把完整 Key 返回给浏览器或写入日志。

## 九、安全与隐私

### 9.1 本地模式

- 只绑定 `127.0.0.1`；
- 无登录是明确的产品选择，不是疏忽；
- 当前 V1：Key 优先从操作系统环境变量读取；没有环境变量时从 Windows DPAPI 加密文件读取；
- 本地分发版：设置页写入本机加密存储（DPAPI），不写 `.env`/localStorage；
- 同一 Windows 账号多人共用时，DPAPI 不能隔离用户；需要独立系统账号或应用内 PIN。

### 9.2 服务器模式

- 必须 HTTPS；
- 必须登录/会话，禁止匿名访问业务接口；
- 使用成熟认证（OIDC/Passkey/成熟库），不自研密码协议；
- 每个用户密钥独立加密，主密钥来自 KMS/环境变量，不落代码库；
- 日志脱敏：不记录 Key、Authorization、完整文档内容；
- 跨租户访问测试是发布门禁；
- 删除/导出/备份保留策略要明确；
- 限流、配额、审计日志从 Beta 阶段开始。

### 9.3 Key 的边界

- Key 是用户凭据，不应由另一个普通用户代填；
- “管理员配置别人的 Key”只在组织共享 Key 模型下成立，需要单独权限和审计；
- 浏览器永远不接触完整 Key（服务器代理调用模型）。

## 十、演进路线

### Phase 0：边界落地（T-4.1 前，已完成主体）

- [ ] 写本 ADR 并评审；

- [ ] 当前 CLI 用 `LocalContext` 调用，不改变建库结果；

验收：当前 121 项测试全绿；本地索引仍为 10 文档 / 4021 chunk；不重新嵌入。

### Phase 1：本地分发版

## 十一、落地顺序

具体任务编号、依赖与完成状态统一由 [开发任务清单](RAG开发任务清单-v1.0.md) 管理；本文不重复维护任务列表。架构上只保留顺序约束：

1. 先落 `RequestContext` / `tenant_id` / `SecretProvider` 边界；
2. 再补 SQLite 文档与任务元数据，Chroma 只做向量索引；
3. 最后做服务器 adapter（Postgres / 对象存储 / Redis / 认证）；
4. 任何阶段都不得为了 ID 方案反复全量重建、反复消耗嵌入额度。

当前已落地的边界：`app/context.py`（RequestContext / SecretProvider）、chunk metadata 的 `tenant_id`、`active` 软删除标记、`app/services` 的文档/任务编排。未落地的部分按任务清单推进。

## 十二、明确不做的事

- 不现在拆微服务；
- 不现在做 Kubernetes；
- 不现在写完整 RBAC/计费；
- 不现在做多租户 UI；
- 不把 Key 存进浏览器 `localStorage` / `sessionStorage`；
- 不把 Key 明文写 SQLite / `.env` / 日志；
- 不因为“未来多用户”而把所有类都抽象一遍；
- 不为了改 chunk_id 反复全量重建、反复消耗嵌入额度。

## 十三、待确认的决策

| # | 问题 | 建议 |
|---|---|---|
| Q1 | 服务器上向量隔离用“每租户 collection”还是“单 collection + tenant filter” | 优先每租户 collection，降低串数据风险 |
| Q2 | 登录方式 | OIDC / Passkey / 成熟库，不自研 |
| Q3 | 是否允许管理员替用户配置 Key | 默认不允许；只允许组织共享 Key 的独立模型 |
| Q4 | 一个用户是否可有多个工作区 | Beta 先一人一租户，后续再加 workspace |
| Q5 | 服务器部署形态 | 单机 Docker Compose 起步，不直接上 K8s |
| Q6 | 本地分发版的密钥存储 | Windows DPAPI 优先，keyring 备选 |

## 十四、验收标准

架构演进是否成功，不看“有没有多租户代码”，而看这些：

- [ ] 本地模式与服务器模式共用同一套应用服务；
- [ ] 换个 adapter 就能从本地 Chroma 切到服务器向量库；
- [ ] 所有查询/删除/任务/Key 都有 tenant 隔离测试；
- [ ] Key 在磁盘/日志/浏览器中都不以明文出现；
- [ ] 软删除、恢复、彻底删除在 DB/向量/文件三处一致；
- [ ] 上传/重建进度通过稳定 Job 接口暴露，不依赖进程内状态；
- [ ] 本地单用户仍能一条命令建库、查询，不被架构复杂度拖慢。
