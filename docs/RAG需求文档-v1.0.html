一句话目标：在本地用 LangChain 搭一套 RAG 问答系统——把 PDF / Word / TXT 导入知识库，提问时用向量检索召回原文片段，交给大模型生成带出处的回答，并通过浏览器页面使用。

0文档使用说明

  • 需求用 FR-xx（功能）与 NFR-xx（非功能）编号，便于逐条对账。
  • 每条需求都带验收标准，做到"可量化、可验证"。
  • 优先级采用 MoSCoW：M 必须有 S 应该有 C 可以有 W V1不做
  • 文中所有参数默认值均标注为「可调」，并给出调整方向。

1项目概述

1.1 背景

日常积累了大量论文、教材与笔记（PDF / Word / TXT）。目前靠人工翻阅与全文搜索定位信息，效率低，且无法回答"跨文档聚合"类问题（如"这几篇论文分别用了什么损失函数"）。需要一个私有、可离线留存知识、按需调用云端模型的问答工具。

1.2 核心目标（可量化）

编号目标量化验收指标
G1文档可顺利导入并检索支持 .pdf/.docx/.txt；随机 10 份文档解析成功率 ≥ 95%
G2检索结果准确自建 20 条测试问答，Top-5 召回命中率 ≥ 85%
G3回答可溯源100% 回答附带来源（文件名 + 页码）；抽查 10 条可溯源率 100%
G4响应速度可接受检索 P95 < 1s；首字 < 3s；单轮完整回答 < 15s
G5工程可复现pip install + 一条命令启动；核心链路有自动化测试

1.3 非目标（V1 明确不做）

项目说明
用户系统 / 登录 / 权限单用户本地使用，不做鉴权
公网部署 / 多租户 / 高可用仅本机 127.0.0.1 访问
混合检索（BM25）+ 重排序列入 V2 预留，V1 不做
图片内容语义理解图注文本会入库，但不做图像语义问答
扫描件 OCRV1 不处理纯扫描 PDF（见风险 R1）
文档在线编辑 / 协作知识库只读+增删，不做编辑
模型微调 / 训练仅调用现成 API
高并发压测单用户，不做并发优化

1.4 术语表

2用户与场景

2.1 目标用户

单用户（本人），本地使用，具备 Python 基础，能自行配置 API Key。

2.2 用户故事

编号用户故事优先级
US-1我把一批 PDF 放进指定目录或上传，系统自动解析入库，无需手工整理M
US-2我提问"这篇论文用了什么损失函数"，系统给出答案并标注来自哪个文件第几页M
US-3我追问"那它的消融实验呢"，系统结合上下文继续回答，不需重复主语S
US-4我发现某篇文档解析有误，可单独删除并重新导入，不影响其他文档S
US-5我想知道知识库里现在有哪些文档，能一眼看到列表S
US-6我暂时不想花钱，希望导入文档时能看到大概花了多少 token / 成本C

2.3 核心使用流程

导入侧： 文档 → 解析(PDF/Word/TXT) → 分块 Chunk → Qwen 向量化 → Chroma 向量库 │ 问答侧： 用户提问 → 问题向量化 → 相似度检索 Top-K ────────────────────────┘ → 组装提示词 → DeepSeek 生成 → 回答 + 来源引用 → 回到用户

FR-01 文档摄入 M

描述：支持两种导入方式——① Web 页面文件上传（单/多选）；② 指定本地目录扫描导入。

  • 支持扩展名：.pdf、.docx、.txt（.md 可选，S）。
  • 单文件大小上限 50 MB（可调）。上传文件落盘到 data/uploads/，保留原始文件。

验收标准

  • 上传一个 50MB 以内 PDF，能成功进入解析流程并给出状态反馈。
  • 目录导入时，非目标扩展名文件被跳过且不报错。

FR-02 文档解析 M

描述：把文档抽取为纯文本，同时尽量保留结构与页码信息。

类型首选方案说明
PDF（文本型）PyMuPDF / pypdf按页抽取文本，记录页码
PDF（含表格）pdfplumber 抽表 → Markdown 表格表格尽量整体保留，避免被切碎
Wordpython-docx + unstructured抽取段落、标题层级、表格
TXT直接读取需编码探测（charset-normalizer），默认 UTF-8
已知限制
数学公式：尽力保留 LaTeX 原文；若 PDF 中公式为图片形式，V1 不做公式识别，会丢失或转为空。图注/标题作为普通文本入库。解析单文件失败不得中断整批导入，需记录失败清单。

验收标准

  • 随机抽 10 份文档，人工核对抽取文本，关键段落无成段缺失。
  • 解析结果中每条文本块都能回溯到 (文件名, 页码)。
  • 引入 1 个损坏文件，其余文件仍正常入库。

FR-03 文本分块 M

使用 RecursiveCharacterTextSplitter（LangChain）按语义边界切块。

参数默认值调整方向
chunk_size500 字符语义碎 → 调大（600–800）；检索不准 → 调小
chunk_overlap80 字符（约 16%）边界丢信息 → 调大
分隔符优先级\n\n → \n → 。 → ； → ！ → ？ → ，面向中文的降级切分
表格块不拆分，整表成块—

每个 chunk 必须携带 source_file、page、chunk_index。

验收标准

  • 抽样 20 个 chunk，句子未被从中间截断（或由 overlap 覆盖）。
  • 表格所在 chunk 未被切散。

FR-04 向量化与入库 M

项目值
嵌入模型text-embedding-v4（阿里云百炼 / DashScope）
向量维度1024（默认；可选 768/512 降本）
单条上限8,192 token
单次批量≤ 10 条（API 硬限制，需分批）
向量库Chroma，持久化目录 data/chroma/
相似度度量cosine
幂等策略以文件内容 SHA-256 判重，已入库重复导入时跳过
重要约束
同一模型若中途更改维度，之前所有向量无法与新向量比较，必须整库重建。V1 固定 1024 维，不得随意改动。

验收标准

  • 入库 N 个 chunk 后，collection.count() == N。
  • 同一文件二次导入，库内数量不增加（幂等生效）。

FR-05 索引管理 S

  • 列出已入库文档（文件名、块数、导入时间）。
  • 按文件删除：删除该文件对应的全部 chunk 向量。
  • 全量重建索引（清空后重新解析入库）。

验收标准

  • 删除某文件后，检索结果中不再出现该文件任何片段。
  • 重建后 count() 与重建前一致（相同输入下）。

FR-06 相似度检索 M

  • 问题侧向量化使用 text_type="query"（若模型支持查询/文档区分优化）。
  • 默认 K = 5（可调 3–10）。
  • 支持按元数据过滤（限定某文件/类型）—— 优先级 C。
  • 检索结果包含：chunk 文本、相似度分数、文件名、页码。

验收标准

  • 返回条数 ≤ K，且按相似度降序排列。
  • 检索 P95 < 1s（不含 LLM 生成）。

FR-07 提示词组装 M

  1. System：角色设定 + 硬约束——只依据上下文回答；上下文不足时明确回复"知识库中没有相关信息"，禁止编造；必须标注引用编号 [n]。
  2. Context：拼接 Top-K 块，每块前加编号 [1] [2] …，并附来源标注。
  3. Question：用户问题（多轮场景为改写后的独立问题）。

Token 控制：上下文总量上限 6,000 token（可调）；超出时按相似度取 Top，丢弃尾部。

验收标准

  • 提示词中每个上下文块都有唯一编号，且能与来源元数据一一对应。
  • 上下文超限时自动截断且不报错。

FR-08 答案生成 M

项目值
模型deepseek-v4-flash（经 OpenAI 兼容接口）
Base URLhttps://api.deepseek.com
上下文窗口1M token（远超本项目需要）
temperature0.2（可调 0.0–0.5，越低越稳）
输出方式流式（SSE / chunked）
无答案兜底上下文不相关时回复固定话术，不瞎猜
注意
deepseek-chat / deepseek-reasoner 两个旧模型名已于 2026-07-24 弃用，请直接使用 deepseek-v4-flash（更强推理可用 deepseek-v4-pro）。

验收标准

  • 给定测试问题，答案为中文、条理清晰。
  • 上下文完全无关时，明确回复"没有相关信息"而非编造。
  • 前端可见流式打字效果。

FR-09 来源引用 / 溯源 M

  • 回答正文内联标注 [1]、[2]。
  • 回答下方列出引用列表：[n] 文件名 · 第 x 页。
  • 前端可展开查看该片段原文。

验收标准

  • 抽查 10 条回答，每条都能追溯到真实存在且语义相关的原文块（可溯源率 100%）。
  • 引用列表中的文件名、页码与库内元数据一致。

FR-10 多轮对话 S

  • 维护会话历史，默认保留最近 5 轮（可调）。
  • 查询改写：把含指代/省略的追问（如"那它的消融实验呢"）结合历史改写为独立查询后再检索 —— 此项是关键，否则追问检索必然失败。
  • 历史持久化：SQLite（data/chat.db）或内存（重启即清）—— 优先级 C。

验收标准

  • 连续 3 轮追问，第 3 轮能正确复用前文主语并检索到相关片段。
  • 历史超过上限时自动丢弃最旧轮次，不报错。

FR-11 Web 界面 M

FastAPI + Jinja2 模板 + 原生 JS（可选 HTMX），单进程部署。

页面路径内容
聊天页/提问输入框、流式回答区、引用展示区、清空会话
文档管理页/documents上传控件、已入库文档列表、删除按钮、重建索引

验收标准

  • 浏览器打开 http://127.0.0.1:8000 可用。
  • 聊天页可完成"提问 → 流式回答 → 看到引用"完整闭环。

4非功能需求（Non-Functional）

NFR-1 性能

指标目标值测量方式
检索耗时（含 query 向量化）P95 < 1s服务端日志打点
首字延迟（TTFT）< 3s前端计时
单轮完整回答< 15s前端计时
单文件索引（≤50 页 PDF）< 60s服务端日志打点
内存占用（空闲）< 1 GB任务管理器

数值基于本地 Chroma + 云端 API。若到云端网络延迟高，可放宽。

NFR-2 可靠性

  • 所有云端 API 调用需有超时（连接 10s / 读取 60s）与重试（最多 3 次，指数退避）。
  • 单文件解析失败不阻断整批导入，失败项进入错误清单并可重试。
  • 向量库写入失败时，保证不产生"半入库"脏数据（按文件原子提交）。

NFR-3 可维护性

  • 分层架构：api（路由）/ core（业务）/ models（数据结构）分离。
  • 全量类型注解，关键函数有 docstring。
  • 统一日志：loguru，输出到控制台 + logs/。
  • 配置外置：所有可调项进 .env，代码不硬编码。

NFR-4 安全与隐私

  • API Key 存于系统环境变量（DEEPSEEK_API_KEY / DASHSCOPE_API_KEY），代码用 os.getenv() 读取；禁止写入代码、.env 或提交仓库。
  • .gitignore 必须排除 .env、data/、logs/。
  • 服务仅绑定 127.0.0.1，不监听 0.0.0.0。
  • 数据流向：文档原文留在本机；仅 chunk 文本片段会发送至 Qwen（嵌入）与 DeepSeek（生成）—— 需使用者知情。

NFR-5 成本（估算）

环节假设成本
首次建库（嵌入）100 文档 × 20 块 × ~400 token ≈ 80 万 tokentext-embedding-v4 $0.07/百万 → ≈ $0.06
单次问答（生成）输入 ~3,000 + 输出 ~400 tokendeepseek-v4-flash → ≈ $0.0005/次
1,000 次问答—≈ $0.5
结论
小规模自用成本极低，瓶颈不在钱，在解析质量与检索准确率。

NFR-6 可复现性

  • 使用 Python venv 隔离依赖（V1 不上 Docker，理由见 §11）。
  • requirements.txt 锁定版本。
  • .env.example 提供配置模板。
  • README.md 含：环境要求、安装、配置、启动、常见问题。
  • 提供一键启动脚本（start.ps1 / start.sh）。

6配置与数据约定

6.1 配置来源：API Key 走系统环境变量

安全约定（已确认）：DEEPSEEK_API_KEY 与 DASHSCOPE_API_KEY 由操作系统环境变量提供（已配置完成），代码通过 os.getenv() 读取，不写入任何文件、不写入 .env、不进版本库。

变量来源行为要求

7.1 验收清单（Definition of Done）

编号验收项判定方法通过线
A1文档导入导入 10 份混合格式文档成功率 ≥ 95%

7.2 测试集构建方法（用于 A2）

  1. 从已入库文档中人工挑选 20 个可明确回答的问题。
  2. 每个问题标注对应的正确来源文件 + 页码（ground truth）。
  3. 跑一遍检索，统计正确来源是否落在 Top-5 内。
  4. 命中数 / 20 = 命中率，需 ≥ 85%（至少 17 条命中）。
  5. 该测试集固化为 tests/eval_questions.json，每次改动检索参数后回归。

7.3 自动化测试范围

  • test_loader.py：三种格式各一份样例，验证解析输出非空且含页码。
  • test_splitter.py：验证块大小在预期区间、overlap 生效、表格块不被切。
  • test_retriever.py：mock 嵌入接口，验证 Top-K 数量与排序。
  • test_api.py：用 TestClient 打通 /api/health、/api/documents 等接口。
