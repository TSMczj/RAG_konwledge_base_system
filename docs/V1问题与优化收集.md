# V1 问题与优化收集

> **用途**：记录使用 V1 时遇到的问题、体验不顺和优化想法，作为 V2 需求评估的输入。
>
> **不是**：V1 任务状态表，也不是已修复事故的根因记录。任务状态看 [开发任务清单](RAG开发任务清单-v1.0.md)，已修问题看 [开发问题排查](README-开发问题排查.md)。
>
> **基线**：V1 / `v0.4-M4`（2026-10-25）
> **维护方式**：每次使用后追加；确认要进入 V2 的条目，先更新需求/架构/API，再进入任务清单。

---

## 一、怎么记录

追加一条时复制下面的模板，分配下一个 `V1-xxx` 编号：

```markdown
### V1-001 一句话标题

- 类型：问题 / 优化 / 能力扩展 / 体验 / 性能 / 安全
- 优先级：P0 / P1 / P2 / P3
- 模块：聊天 / 检索 / 文档 / 设置 / 多轮 / 部署 / UI / 其他
- 状态：待评估 / 已确认 / V2候选 / 暂缓 / 已缓解 / 已修复
- 首次记录：YYYY-MM-DD
- 场景：在什么操作下遇到
- 现象：实际发生了什么
- 期望：希望它变成什么样
- 影响：对使用/数据/成本的影响
- 备注：截图路径、日志、相关文件或讨论链接
```

规则：

1. **一条只描述一个问题或一个想法**，不要把多个问题塞进同一条。
2. **不记录完整 API Key、文档正文、个人信息**；需要举例时用脱敏后的片段。
3. **优先级不是排期承诺**：P0/P1 先评估是否影响 V1 正常使用，P2/P3 作为 V2 候选。
4. **状态变更要留痕**：`待评估 → 已确认 → V2候选/暂缓`；修复后写解决方式和提交号。
5. 进入 V2 实现前，必须把确认后的条目转成需求编号（FR/NFR）或架构/API 变更，不能直接照着这条描述写代码。

### 编号与状态

- `P0`：完全阻塞使用或可能损坏数据，需要立即处理。
- `P1`：核心流程明显受阻，有临时绕行方案。
- `P2`：影响效率或体验，V2 优先候选。
- `P3`：锦上添花、长期演进。

- `待评估`：刚记录，还没判断是否值得做。
- `已确认`：问题/需求成立，等待排期。
- `V2候选`：明确进入 V2 需求池。
- `暂缓`：当前不做，保留记录。
- `已缓解`：V1 有绕行方案，但根因未消除。
- `已修复`：已解决，补提交号/验证方式。

## 三、条目

### V1-001 多模型只有 DeepSeek 实际可用

- 类型：能力扩展
- 优先级：P1
- 模块：设置 / 聊天
- 状态：V2候选
- 首次记录：2026-10-25
- 场景：想在聊天页切换 ChatGPT / Claude / GLM / MiMo。
- 现象：设置页有 OpenAI / Anthropic 卡片，但标记“未接入”；聊天模型选择器只有 DeepSeek 可用。
- 期望：Provider 注册表 + OpenAI-compatible / Anthropic 适配器；每个 provider 独立 Key、模型列表、默认模型；每条回答保留实际模型。
- 影响：V1 只能使用 DeepSeek，换模型需要改代码或配置。
- 备注：需要先做 L2 文档更新（FR-13、API `model_id`、架构 Provider 边界），见 `prototype/ui` 的模型选择器原型。

### V1-002 会话历史仅内存，重启后丢失

- 类型：体验
- 优先级：P2
- 模块：多轮
- 状态：V2候选
- 首次记录：2026-10-25
- 场景：连续追问后重启服务，再继续问“它呢”。
- 现象：历史清空，追问无法复用前文主语。
- 期望：V2 可选 SQLite 会话持久化，或在 UI 明确提示“重启后历史清空”。
- 影响：长会话体验中断。
- 备注：当前默认保留最近 5 轮，内存实现见 `app/services/sessions.py`。

### V1-003 全量重建耗时长、消耗嵌入额度，缺少取消/断点

- 类型：优化
- 优先级：P2
- 模块：文档 / 索引
- 状态：待评估
- 首次记录：2026-10-25
- 场景：文档有改动后执行“重建整个索引”。
- 现象：重建会重新消耗嵌入额度，耗时较长；没有取消，也没有从上次进度继续。
- 期望：重建前显示预估 chunk/额度；支持取消、失败重试和分段进度。
- 影响：误操作成本较高，等待时间长。
- 备注：V1 验收时未重跑全量重建以保护嵌入额度。

### V1-004 上传/重建 job 状态仅内存，重启丢失

- 类型：可靠性
- 优先级：P2
- 模块：文档 / 任务
- 状态：V2候选
- 首次记录：2026-10-25
- 场景：上传大文件或重建过程中重启服务。
- 现象：内存 job 表丢失，前端轮询找不到任务；失败后上传只能重新选择文件。
- 期望：任务持久化、重启恢复/明确标记中断、失败可重试。
- 影响：长任务可靠性不足。
- 备注：当前 `app/services/jobs.py` 是单进程内存任务表。

### V1-005 统一错误结构 / X-Request-ID 未落地

- 类型：工程规范
- 优先级：P2
- 模块：API
- 状态：已确认
- 首次记录：2026-10-25
- 场景：设置错误 Key、上游超时或参数错误时排查。
- 现象：错误体仍包含 FastAPI 默认结构，部分错误没有稳定的 `request_id`。
- 期望：所有接口统一 `{code,message,detail,retryable,request_id}`，响应头带 `X-Request-ID`。
- 影响：前端错误处理和日志关联不够稳定。
- 备注：API 契约 §1.3/§1.4 已定义目标结构，实现状态仍为待补。

### V1-006 document_id 仍使用 file_hash

- 类型：数据模型
- 优先级：P2
- 模块：文档 / API
- 状态：已确认
- 首次记录：2026-10-25
- 场景：删除/恢复文档、未来切换服务器存储。
- 现象：`document_id` 当前是内容哈希；文件内容变化后身份变化，不适合作为长期业务主键。
- 期望：V2 切换 ULID 或其他稳定 ID，文件哈希只做去重。
- 影响：数据迁移和外部链接稳定性。
- 备注：API 契约 §1.5 已把 ULID 列为目标。

### V1-007 多轮查询改写增加首字延迟

- 类型：性能
- 优先级：P2
- 模块：多轮 / 生成
- 状态：待评估
- 首次记录：2026-10-25
- 场景：连续追问时，首字前要先做一次查询改写。
- 现象：多轮追问比单轮多一次 LLM 调用，首字时间增加。
- 期望：更轻量的改写策略（规则/小模型/缓存），或流式展示“正在理解追问”。
- 影响：追问体感变慢。
- 备注：V1 仅在检测到指代/省略时触发改写；单轮不触发。

### V1-008 来源侧栏的表格片段以原始 Markdown 呈现

- 类型：体验
- 优先级：P2
- 模块：UI / 引用
- 状态：已修复
- 首次记录：2026-10-25
- 场景：查看 PDF 表格、图片类来源的原文片段。
- 现象：表格在来源卡片里是带 `| --- |` 和 `<br>` 的原始文本，读起来吃力；图片类来源没有缩略图。

- 影响：核对表格/图片数据效率低，结构图碎片看起来像乱码。
- 备注：2026-10-26 已实现表格 Markdown → HTML 渲染、`<br>` 还原、展开/折叠；图片缩略图仍在 V1-013。假表过滤同时收紧（填充率/有效行/特殊 token）。

### V1-009 OpenAI / Anthropic 配置卡显示“未接入”

### V1-012 DPAPI 同一 Windows 账号不隔离用户

- 类型：安全
- 优先级：P3
- 模块：设置 / 安全
- 状态：暂缓
- 首次记录：2026-10-25
- 场景：多个家庭成员/同事共用同一个 Windows 账号。
- 现象：同一账号下，DPAPI 加密 Key 对所有该账号进程可解密。

### V1-013 PDF / 独立图片未进入 RAG 链路

- 类型：能力扩展
- 优先级：P1
- 模块：文档 / 检索 / 生成 / UI
- 状态：V2候选
- 首次记录：2026-10-26
- 场景：PDF 里的结构图、流程图、图表、扫描页，以及独立上传的截图/照片；用户的问题需要看图才能回答。
- 现象：当前 loader 只抽文本和表格，图片被完全忽略；扫描页没有文本层时只告警、不入库；BERT 第 3/15/16 页结构图里的文字被 pdfplumber 误判成表格，来源栏只能看到 Markdown 碎片；DeepSeek 调用只发文本，没有传原图的路径。
- 期望：V2 增加图片处理链路——抽图 / 独立图片上传 → OCR / 图注 / Flash Vision 摘要 → 以文本 chunk 入库（`kind=image`、`image_path`、`page`、`bbox`）→ 文本检索 → 生成时把原图交给 DeepSeek Flash；来源面板显示缩略图/原图；可选图像向量与 `qwen3-vl-rerank`。
- 影响：图表和扫描件内容无法被检索、回答或核对；结构图碎片会污染检索结果与引用展示。
- 备注：先评估 MinerU / PaddleOCR / VLM caption 的本地可行性。当前机器为 RTX 3060 Laptop 6GB，MinerU 建议 `basic` 档更稳；图片二进制不进 Chroma，只存路径和 metadata。需要新增多模态模型与成本边界评估，V1 不实现。官方 `deepseek-flash` 已支持 Vision（项目使用的旧名 `deepseek-v4-flash` 也由 V4.1-Flash-1017 承接），V2 可优先评估「摘要/OCR 检索 + 原图交 Flash 回答」，不必先引入新的 VLM provider；`deepseek-v4-pro` 不支持视觉，切换时注意。

### V1-014 Markdown / README / HTML 未覆盖，非 PDF 无章节级引用

- 类型：能力扩展
- 优先级：P1
- 模块：文档 / 解析 / 检索 / UI
- 状态：V2候选
- 首次记录：2026-10-26
- 场景：上传 `README.md`、技术文档、网页 HTML；希望引用到章节而不是页码。
- 现象：`ALLOWED_SUFFIXES` 只有 `.pdf/.docx/.txt`，前端 `accept` 同样；loader 没有 Markdown/HTML；非 PDF 的 `page=0`，来源栏只能显示“无页码”，无法定位章节；HTML 整页拍平会把导航、页脚、脚本带进向量。
- 期望：支持 `.md/.markdown/.html/.htm`；Markdown 按标题分节，保留代码块、表格、列表；HTML 用 trafilatura/readability 提正文 + lxml 抽表格，清掉 nav/script/style；metadata 增加 `section`、`heading_path`、`source_url`；上传白名单和前端 `accept` 同步；来源卡片显示“章节”而不是“第 x 页”；补 loader 测试。
- 影响：README 和网页资料无法入库；非 PDF 文档即使入库也无法按章节核对。
- 备注：L2 变更，需要先改需求 FR-01/FR-02、API metadata、任务清单；不引入大模型，工作量主要在解析边界和引用 UI。与 V1-008 / V1-017 联动。

### V1-015 扫描 PDF / 复杂版式没有 OCR 与版式解析

- 类型：能力扩展
- 优先级：P1
- 模块：文档 / 解析 / 部署
- 状态：V2候选
- 首次记录：2026-10-26
- 场景：扫描件、图片型 PDF、多栏论文、复杂表格和公式。
- 现象：当前只抽文本层；没有文本层的页面只告警、不 OCR，最终 0 chunk；复杂版式的表格容易被 pdfplumber 误判。
- 期望：数字版 PDF 继续走原生 loader；扫描件/复杂版式用 MinerU 4.0 独立 sidecar，增加 `PDF_PARSER=auto|native|mineru`；读取 `structured_content` / `middle_json`，把 `page_idx`（0-based，+1）、text/table/equation blocks 映射成现有 Segment；按 `file_hash + parser + tier` 缓存；失败时告警/回退，不阻断其他文件。
- 影响：扫描件和复杂版式无法检索，是当前覆盖率最大的空洞。
- 备注：RTX 3060 Laptop 6GB → MinerU `basic` 档更稳，`standard` 可能吃紧；MinerU 4.0 是 Apache 2.0 + 附加条款；必须独立 `.mineru` 环境/端口，不混进主 venv。先拿 `bert.pdf` + 一份扫描样本做 PoC；MinerU 抽出的图片仍需 V1-013 的 caption/原图链路。

### V1-016 大语料只有纯向量检索，缺 BM25 与 rerank

- 类型：优化
- 优先级：P1
- 模块：检索 / 生成
- 状态：V2候选
- 首次记录：2026-10-26
- 场景：语料长期增大；型号、错误码、参数名、专有名词需要精确匹配；表格/结构图碎片可能获得较高相似度。
- 现象：当前是 Chroma dense Top-5 + `MIN_SCORE=0.25`，没有 BM25、没有 rerank；精确词可能漏召回，低相关片段可能进上下文。
- 期望：dense + BM25 混合（RRF 融合），先召回 Top-20~50，再用 `qwen3-rerank` 精排到 Top-5；增加 `candidate_k` / rerank 配置；有 rerank 时把 `MIN_SCORE` 降到 0.1~0.15 保召回；用评估集验证 recall/MRR/延迟。
- 影响：大语料下的召回率和精度，直接决定回答质量。
- 备注：Chroma 没有 BM25，可先用 `rank_bm25 + jieba` 或 SQLite FTS5 做本地 sidecar，不迁移向量库；`qwen3-rerank` API 先跑通，本地小模型后置；rerank 预计增加 200~500ms。

### V1-017 分块与 chunk 上下文偏弱

- 类型：优化
- 优先级：P2
- 模块：分块 / 检索
- 状态：V2候选
- 首次记录：2026-10-26
- 场景：长文档、跨页/跨节问题、代码块和表格。
- 现象：`RecursiveCharacterTextSplitter` 500/80 字符切分；heading 不参与切分；embedding 的文本没有文件/页/章节上下文（这些只出现在 prompt 的 source block 里）；chunk 边界可能断章。
- 期望：heading-aware / parent-child / small-to-big；代码块和表格整块保留；embedding 前加确定性上下文头（文件、页、章节）；可选 LLM contextual retrieval；按格式配置 chunk size。
- 影响：检索歧义、跨节问题答不全。
- 备注：Anthropic Contextual Retrieval 报告 contextual embeddings + BM25 可降低 49% 检索失败率，加 rerank 到 67%；但有一次性 LLM 成本。当前 282 chunk 很小，扩格式后重评；与 V1-014 的元数据一起做。

## 四、从记录到 V2

3. **转需求**：V2 候选必须落到需求文档的 FR/NFR（或明确写成架构/API 变更），不能只停留在本文件。
4. **更新契约**：涉及接口的，先改 [API 契约](API契约-v1.0.md)；涉及安全/存储的，先改 [架构演进设计](架构演进设计.md)。
5. **拆任务**：确认后再写入 V2 任务清单，不在本文件里维护代码任务状态。
6. **闭环**：修复后更新本条目状态、解决方式和提交号；已修复条目不删除，保留决策痕迹。
