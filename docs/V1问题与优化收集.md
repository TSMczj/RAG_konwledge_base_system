# V1 问题与优化收集

> **用途**：记录使用 V1 时遇到的问题、体验不顺和优化想法，作为 V2 需求评估的输入。
>
> **不是**：V1 任务状态表，也不是已修复事故的根因记录。任务状态看 [开发任务清单](RAG开发任务清单-v1.0.md)，已修问题看 [开发问题排查](README-开发问题排查.md)。
>
> **基线**：V1 / `v0.4-M4`（2026-10-25）
> **维护方式**：每次使用后追加；确认要进入 V2 的条目，先更新需求/架构/API，再进入任务清单。

---

## 一、怎么记录

追加一条时复制下面的模板，分配下一个 `V1-xxx` 编号：

```markdown
### V1-001 一句话标题

- 类型：问题 / 优化 / 能力扩展 / 体验 / 性能 / 安全
- 优先级：P0 / P1 / P2 / P3
- 模块：聊天 / 检索 / 文档 / 设置 / 多轮 / 部署 / UI / 其他
- 状态：待评估 / 已确认 / V2候选 / 暂缓 / 已缓解 / 已修复
- 首次记录：YYYY-MM-DD
- 场景：在什么操作下遇到
- 现象：实际发生了什么
- 期望：希望它变成什么样
- 影响：对使用/数据/成本的影响
- 备注：截图路径、日志、相关文件或讨论链接
```

规则：

1. **一条只描述一个问题或一个想法**，不要把多个问题塞进同一条。
2. **不记录完整 API Key、文档正文、个人信息**；需要举例时用脱敏后的片段。
3. **优先级不是排期承诺**：P0/P1 先评估是否影响 V1 正常使用，P2/P3 作为 V2 候选。
4. **状态变更要留痕**：`待评估 → 已确认 → V2候选/暂缓`；修复后写解决方式和提交号。
5. 进入 V2 实现前，必须把确认后的条目转成需求编号（FR/NFR）或架构/API 变更，不能直接照着这条描述写代码。

### 编号与状态

- `P0`：完全阻塞使用或可能损坏数据，需要立即处理。
- `P1`：核心流程明显受阻，有临时绕行方案。
- `P2`：影响效率或体验，V2 优先候选。
- `P3`：锦上添花、长期演进。

- `待评估`：刚记录，还没判断是否值得做。
- `已确认`：问题/需求成立，等待排期。
- `V2候选`：明确进入 V2 需求池。
- `暂缓`：当前不做，保留记录。
- `已缓解`：V1 有绕行方案，但根因未消除。
- `已修复`：已解决，补提交号/验证方式。

## 三、条目

### V1-001 多模型只有 DeepSeek 实际可用

- 类型：能力扩展
- 优先级：P1
- 模块：设置 / 聊天
- 状态：V2候选
- 首次记录：2026-10-25
- 场景：想在聊天页切换 ChatGPT / Claude / GLM / MiMo。
- 现象：设置页有 OpenAI / Anthropic 卡片，但标记“未接入”；聊天模型选择器只有 DeepSeek 可用。
- 期望：Provider 注册表 + OpenAI-compatible / Anthropic 适配器；每个 provider 独立 Key、模型列表、默认模型；每条回答保留实际模型。
- 影响：V1 只能使用 DeepSeek，换模型需要改代码或配置。
- 备注：需要先做 L2 文档更新（FR-13、API `model_id`、架构 Provider 边界），见 `prototype/ui` 的模型选择器原型。

### V1-002 会话历史仅内存，重启后丢失

- 类型：体验
- 优先级：P2
- 模块：多轮
- 状态：V2候选
- 首次记录：2026-10-25
- 场景：连续追问后重启服务，再继续问“它呢”。
- 现象：历史清空，追问无法复用前文主语。
- 期望：V2 可选 SQLite 会话持久化，或在 UI 明确提示“重启后历史清空”。
- 影响：长会话体验中断。
- 备注：当前默认保留最近 5 轮，内存实现见 `app/services/sessions.py`。

### V1-003 全量重建耗时长、消耗嵌入额度，缺少取消/断点

- 类型：优化
- 优先级：P2
- 模块：文档 / 索引
- 状态：待评估
- 首次记录：2026-10-25
- 场景：文档有改动后执行“重建整个索引”。
- 现象：重建会重新消耗嵌入额度，耗时较长；没有取消，也没有从上次进度继续。
- 期望：重建前显示预估 chunk/额度；支持取消、失败重试和分段进度。
- 影响：误操作成本较高，等待时间长。
- 备注：V1 验收时未重跑全量重建以保护嵌入额度。

### V1-004 上传/重建 job 状态仅内存，重启丢失

- 类型：可靠性
- 优先级：P2
- 模块：文档 / 任务
- 状态：V2候选
- 首次记录：2026-10-25
- 场景：上传大文件或重建过程中重启服务。
- 现象：内存 job 表丢失，前端轮询找不到任务；失败后上传只能重新选择文件。
- 期望：任务持久化、重启恢复/明确标记中断、失败可重试。
- 影响：长任务可靠性不足。
- 备注：当前 `app/services/jobs.py` 是单进程内存任务表。

### V1-005 统一错误结构 / X-Request-ID 未落地

- 类型：工程规范
- 优先级：P2
- 模块：API
- 状态：已确认
- 首次记录：2026-10-25
- 场景：设置错误 Key、上游超时或参数错误时排查。
- 现象：错误体仍包含 FastAPI 默认结构，部分错误没有稳定的 `request_id`。
- 期望：所有接口统一 `{code,message,detail,retryable,request_id}`，响应头带 `X-Request-ID`。
- 影响：前端错误处理和日志关联不够稳定。
- 备注：API 契约 §1.3/§1.4 已定义目标结构，实现状态仍为待补。

### V1-006 document_id 仍使用 file_hash

- 类型：数据模型
- 优先级：P2
- 模块：文档 / API
- 状态：已确认
- 首次记录：2026-10-25
- 场景：删除/恢复文档、未来切换服务器存储。
- 现象：`document_id` 当前是内容哈希；文件内容变化后身份变化，不适合作为长期业务主键。
- 期望：V2 切换 ULID 或其他稳定 ID，文件哈希只做去重。
- 影响：数据迁移和外部链接稳定性。
- 备注：API 契约 §1.5 已把 ULID 列为目标。

### V1-007 多轮查询改写增加首字延迟

- 类型：性能
- 优先级：P2
- 模块：多轮 / 生成
- 状态：待评估
- 首次记录：2026-10-25
- 场景：连续追问时，首字前要先做一次查询改写。
- 现象：多轮追问比单轮多一次 LLM 调用，首字时间增加。
- 期望：更轻量的改写策略（规则/小模型/缓存），或流式展示“正在理解追问”。
- 影响：追问体感变慢。
- 备注：V1 仅在检测到指代/省略时触发改写；单轮不触发。

### V1-008 来源侧栏的表格片段以原始 Markdown 呈现

- 类型：体验
- 优先级：P3
- 模块：UI / 引用
- 状态：待评估
- 首次记录：2026-10-25
- 场景：查看 PDF 表格来源的原文片段。
- 现象：表格在来源卡片里是带 `| --- |` 的原始文本，读起来吃力。
- 期望：识别表格片段并渲染为简单表格，或提供“查看原页”入口。
- 影响：核对表格数据效率低。
- 备注：来源数据已带 `kind=table`，前端可按 kind 分流。

### V1-009 OpenAI / Anthropic 配置卡显示“未接入”

- 类型：体验
- 优先级：P2
- 模块：设置
- 状态：已确认
- 首次记录：2026-10-25
- 场景：打开设置页查看生成模型 provider。
- 现象：两张卡存在但按钮禁用，用户会疑惑“为什么有卡但不能配”。
- 期望：明确标注“V2 规划”，或暂时隐藏未接入 provider。
- 影响：设置页信息噪音。
- 备注：与 V1-001 相关；多模型落地后应同步取消禁用。

### V1-010 PowerShell 执行策略阻止 start.ps1 直接运行

- 类型：部署
- 优先级：P3
- 模块：启动
- 状态：已缓解
- 首次记录：2026-10-25
- 场景：双击或在未放宽执行策略的 PowerShell 中运行 `start.ps1`。
- 现象：提示脚本未数字签名，无法执行。
- 期望：提供无策略障碍的一键入口，或签名脚本。
- 影响：首次启动多一步绕行。
- 备注：已提供 `start.cmd`，通过 `-ExecutionPolicy Bypass` 调用；V1 README 已说明。

### V1-011 单用户、无登录，不能直接多用户部署

- 类型：架构
- 优先级：P3
- 模块：部署 / 安全
- 状态：暂缓
- 首次记录：2026-10-25
- 场景：想把服务放到局域网或公网供多人使用。
- 现象：V1 固定 `tenant_id=local`，无认证和租户隔离。
- 期望：V2 服务器模式：登录、tenant 隔离、每用户密钥库。
- 影响：当前只能单机单用户使用。
- 备注：属于产品定位外的演进，不阻塞 V1 本地使用。

### V1-012 DPAPI 同一 Windows 账号不隔离用户

- 类型：安全
- 优先级：P3
- 模块：设置 / 安全
- 状态：暂缓
- 首次记录：2026-10-25
- 场景：多个家庭成员/同事共用同一个 Windows 账号。
- 现象：同一账号下，DPAPI 加密 Key 对所有该账号进程可解密。
- 期望：独立系统账号，或应用内 PIN/用户密钥库。
- 影响：本机共享账号场景的密钥隔离不足。
- 备注：V1 的定位是单用户本机运行；文档已注明该边界。

## 四、从记录到 V2

1. **先评估**：是否能复现、影响范围、是否有绕行方案。
2. **定优先级**：P0/P1 先判断是否要在 V1 维护版修复；P2/P3 进入 V2 候选。
3. **转需求**：V2 候选必须落到需求文档的 FR/NFR（或明确写成架构/API 变更），不能只停留在本文件。
4. **更新契约**：涉及接口的，先改 [API 契约](API契约-v1.0.md)；涉及安全/存储的，先改 [架构演进设计](架构演进设计.md)。
5. **拆任务**：确认后再写入 V2 任务清单，不在本文件里维护代码任务状态。
6. **闭环**：修复后更新本条目状态、解决方式和提交号；已修复条目不删除，保留决策痕迹。
