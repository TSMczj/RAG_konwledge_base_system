## 三、写文档的规则

1. **一个事实只写一次。** 其他位置用链接或编号引用，例如“见 API 契约 §三”。
2. **状态只放在一个地方。** 任务完成状态以任务清单的复选框为准；README 和进度文档只写摘要。
3. **接口只放在一个地方。** 所有路径、字段、错误码、job 状态以 API 契约为准；需求/架构不再列具体路由。
4. **历史快照要标注时间。** 问题排查是分阶段归档，不冒充当前状态。
5. **每份文档头部写清：状态、版本、基线/最后核对时间。**

## 四、变更分级

不是所有变更都从需求文档开始。先判断变更类型，再决定起点。

| 级别 | 典型变更 | 起点文档 | 是否改需求 |
|---|---|---|---|
| **L0 文案/样式** | 按钮文案、间距、颜色、纯展示 | UI/README | 只有改变验收口径才改 |
| **L1 修复/重构** | 修 bug、拆函数、换实现 | 任务清单 + 测试 + 问题排查 | 不硬造需求 |
| **L2 功能/接口** | 新增导出、改 SSE 字段、加筛选、改路由 | **需求文档** | 必须更新范围/验收 |
| **L3 架构/安全/数据** | 加租户、换存储、改 Key 策略、改数据模型 | **架构文档** | 只补约束，不写接口细节 |

判断标准只有一句：**这次变化会不会让另一份文档里的现有描述变成错的？** 会，就必须更新；不会，就只加链接。

## 五、一次变更的流程

### 1. 先写五句话提案

```text
变更：
类型：新增 / 修改 / 修复 / 重构
是否属于当前 V1/M3：现在做 / 进 backlog
影响：需求 / 架构 / API / 数据 / UI
文档动作：需要更新哪几份
```

这一步先回答“现在该不该做”。和当前里程碑无关的功能进 backlog/V2，不直接改 V1 需求。

### 2. 按类型决定顺序

**L2 / L3：文档先行**

1. 先改唯一事实源：需求或架构；
2. 再改 API 契约（接口/字段/状态变化时）；
3. 再改任务清单（新增任务、依赖、验收）；
4. 写代码和测试；
5. 更新 README / UI 说明；
6. 最后更新进度文档，只做摘要。

**L1 修复：**

1. 任务清单或 bug 记录；
2. 代码 + 回归测试；
3. 问题排查文档；
4. 进度摘要。

**L0 文案/样式：**

1. UI/README 直接改；
2. 若改变验收口径，回到 L2 更新需求。

### 3. 同一变更闭环

文档更新和代码放在同一个任务/提交里完成，不把“文档稍后补”留到下一阶段。任务标记完成前，文档必须已经同步。

## 七、完成定义与阶段对账

### 任务 DoD 增加第 5 条

1. 代码能跑通；
2. 交付物落到指定路径；
3. 满足该条验收口径；
4. 可调参数进配置；
5. **文档已同步：唯一来源已更新，其他文档只加链接，没有新的重复副本。**

### 阶段出口做一次文档对账

每个 Sprint 结束时检查：

- 需求 FR/A 编号是否有未回填状态；
- API 契约的“实现状态”是否和代码一致；
- 任务清单复选框是否和实际提交一致；
- 进度文档是否只是摘要、没有复制正文；
- 问题排查是否标了快照日期；
- 文档相对链接是否有效。

这一步应作为固定任务，而不是临时想起来。
